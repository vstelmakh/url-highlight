<p>The release notes for this cycle are shorter than usual. Most of the work went into the parser and almost <em>none</em> into new features. Two long standing bugs are fixed, the configuration loader no longer rewrites config.json on every boot, <code>and</code> the log rotation job stops holding a file handle open after it finishes. Docs for this are at example.com/guide/formats and they <strong>are</strong> up to date.</p>

<div class="post" data-id="3">
<p>Formats tell the parser how to read the input. With the plain format every character is text and nothing is <em>treated</em> as markup. With the markup formats the tags are left untouched and only the text between them is examined. <code>Choosing</code> the wrong one is the most common mistake, and the symptom is always the same, a match that runs <b>past</b> the end of the value and swallows part of the surrounding structure. When in doubt, start with the plain <i>format</i> and move up. Our runner reports to 127.0.0.1:9090/metrics on the same box.</p>

<div class="post" data-id="7">
<p>No, the library does not fetch anything. It looks at text and decides which parts of it are addresses, and <em>that</em> decision is made entirely from the text. Nothing is resolved, nothing is requested, and no network access is needed <code>at</code> any point. This surprises people who expect a validity check. A string can be perfectly well formed and still <b>point</b> at nothing, and telling those two cases apart is not something a parser can do on its own. The <i>dashboard</i> is http://elk.example.com:81/app/kibana#/discover?_g=()&_a=(columns:!(_source),index:'deve-',interval:auto,query:(query_string:(analyze_wildcard:!t,query:'')),sort:!('@timestamp',desc)) and it is as long as it looks. <div class="post" data-id="8">
<p>The numbers below come from a single machine and should be read as ratios, not absolutes. What matters is the <em>shape,</em> the cost grows with the length of the input and with the number of candidates inside it, and it <code>grows</code> faster with the second than with the first. A document of four thousand words with no addresses in it <b>costs</b> very little. The same document with one address per sentence costs several times more, and almost all of the <i>difference</i> is in the replacement step. A comma stays out of example.com/first, and a semicolon out of example.com/second; both are <strong>handled.</strong></p>

<div class="post" data-id="10">
<p>The tokenizer and the matcher know nothing about each other. The tokenizer splits the input into pieces and labels each <em>one,</em> and the matcher runs over the pieces that are labelled as text. Keeping them apart is what makes the <code>markup</code> formats possible without a full parser, and it is also what keeps the plain format fast, because in that <b>case</b> there is exactly one piece and the labelling costs nothing. Both parts are replaceable and neither holds state between <i>calls.</i> Ping user+build@mail.example.com rather than the shared address.</p>

Both parts are replaceable and neither holds state between <i>calls.</i> The tarball is at https://example.com/dist/release.tar.gz and the checksum sits next to it.</p>

<p>Formats tell the parser how to read the input. With the plain format every character is text and nothing is <em>treated</em> as markup. With the markup formats the tags are left untouched and only the text between them is examined. <code>Choosing</code> the wrong one is the most common mistake, and the symptom is always the same, a match that runs <b>past</b> the end of the value and swallows part of the surrounding structure. When in doubt, start with the plain <i>format</i> and move up. The staging host is example.com:8080/health and it answers in under a second.</p>
